# Phase 0 · 研究与取舍

## 离线运行与开发验证

- **决定** — 以 TypeScript 和 Node.js 24 LTS 作为开发验证基线。对局跨层契约以业务语义描述，本地开发可以同进程连接，浏览器开发界面通过本机适配接入。运行资源随本地交付提供。
- **依据** — 旧版主体是 JavaScript，沿用相近运行环境降低迁移成本。以 SQLite 为运行时目录，便于先验证构筑直读及版本发布。
- **备选** — 单 HTML、桌面封装、本地服务加浏览器均可后续比较。单 HTML 方案还需要验证运行时 SQLite 写入、文件权限和持久化，当前仍待决定最终交付形态。

## 旧版行为基线

- **决定** — 用旧版 2D / 3D 源文件建立可重复输入与预期输出，逐步捕获状态、随机结果和语义事件。回放先验证一场含随机路径的完整终局。
- **依据** — 既有脚本共享对局全局状态，部分规则在界面脚本中，V6 使用克隆态试算，百川包含随机洗混。只对比最终胜负会遗漏关键结算差异。
- **备选** — 从裁决书直接重写规则会混入行为变更，既有回放可用作样本来源，需单独确认其复现范围。

## 统一玩家契约与 AI

- **决定** — 玩家端和 AI 复用席位契约。核心保存待决策项和恢复位置。模型收到行动请求后产出决定，实际动作由 AI 适配器提交。旧 V6 的试算通过受限内部适配器迁移。
- **依据** — 「炽羽」、回响和冰泉都可能需要暂停结算。让各端重建结算会让规则重复。隔离试算便于保留旧模型行为并支持新模型接入。
- **备选** — 让模型直接修改真实对局会绕过席位裁定。最终允许的试算字段及访问条件见计划 PEND-02、PEND-03。

## 数据版本与验证

- **决定** — SQLite 管理已发行卡池，构筑以版本查询，对局以固定快照结算。草稿发布前整体校验并事务写入。使用核心和契约测试、浏览器流程验证、版本发布失败验证。
- **依据** — 构筑可以查询当前发行版，历史样本和进行中对局仍可追溯到原版本。
- **备选** — 就地改写发行版会使旧卡组和回放失去确定引用。用户卡组具体存储方式可替换。

## 后续讨论

交付形态、最终 SQLite 驱动、旧卡组与回放兼容范围、EVE 自动运行控制与观战界面仍待确认。三项跨层待办由 [plan.md](plan.md#待明确事项) 统一跟踪，本文的技术取舍仅用于拟定 Phase 1 草案。
