# Feature Specification — 《临界》离线工程化重构

**Feature Branch** — 实施分支为 `work`，跟踪 `origin/work`\
**Created** — 2026-11-24  
**Status** — 已澄清，进入实现计划
**Input** — 项目章程及已讨论的离线对局、双前端、可替换 AI、构筑和卡池发布场景

首版仅供本项目开发者开发、运行和排障。面向普通玩家的广泛发行及相关权限和分享体验另行规划。「玩家」在本规格中表示对局中的操作角色。首版对局范围为真人对 AI（PVE）及 AI 对 AI（EVE）初始化。双人 PvP 留待后续版本规划。

## Clarifications

### Session 2026-11-24

- Q: 工程化重构的规格扩展和待明确事项记录在哪里？ → A: 记录在本规格，当前阶段止于规格澄清。
- Q: 项目按哪些最高层划分业务职责和状态所有权？ → A: 沿用章程的玩家端与观战端层、对局层、AI 决策层、构筑与卡池层。
- Q: 如何表达跨层业务交互？ → A: 只使用 Command、Query、Event。命令受理或拒绝与查询结果沿各自原交互返回。事件通知已发生的事实，接收方可发起下一次独立交互。

### Session 2026-11-25

- Q: 首版的统一对局协议，需要对独立开发、自行升级的客户端承诺多大范围的兼容性？ → A: 支持客户端独立开发和更新。同一协议版本内，命令、查询和事件的业务标识及含义保持稳定，兼容的客户端与核心可以独立升级。

- Q: 首版应允许哪些 AI 模型在试算时读取本席位看不到的真实对局信息，例如对手手牌或未抽牌的顺序？ → A: 所有模型的试算均限于本席位可见信息。若确认旧 V6 依赖隐藏信息，标注依赖和受影响行为，尽快退役 V6。将开发遵守该边界的新模型列入首版规划。本项的首版 V6 结论由 2026-11-26 的澄清更新。

- Q: 首版遇到重复提交、过期动作或迟到的 AI 决定时，对局核心需要保证到什么程度？ → A: 同一命令最多结算一次，过期动作和迟到的 AI 决定须拒绝。同一会话重新接入后，授权席位重试已确认受理的同一命令可取得原回执。本地程序异常中断或正常退出后，重启须可恢复未结束的对局、待决策项和命令处理结果。

- Q: 程序重启后，应直接恢复核心上次确认的局面，还是依据已经发生的对局历史重建局面？ → A: 重启直接载入最近一次确认的权威状态，同时保留完整的对局日志和状态记录，支持在独立的复现环境中重建任意已确认的对局中间状态，用于复现缺陷和验证。

- Q: 卡牌效果应优先由通用规则步骤组合，还是由各类效果分别定义自己的结算流程？ → A: 优先组合通用规则步骤。若旧版卡牌效果在触发或结算结构上差异显著，则专门设计统一的卡牌效果抽象，并按该抽象批量重构卡池中的卡牌效果定义。

- Q: AI 要试算一个动作的结果时，应该由正式对局的同版规则来结算，还是由 AI 模型自己估算？ → A: 对局层提供与游戏核心同步的正式规则解算器，供模型按需使用。统一模型接口须支持依赖解算器的束搜索模型，也须支持无需解算器即可生成行动的模型，包括未来基于游戏数据训练的机器学习模型。

- 游戏主体可在手机和电脑安装，首次装好后每台设备可独立离线运行。
- 官方 2D、3D 前端按需安装。正式版启动器支持从本地文件安装第三方前端，并在离线状态下打开已安装前端。
- 卡组存于各设备，通过文件导入导出迁移。

### Session 2026-11-26

- Q: 已获席位授权的命令因对局规则被拒后，原样重试应返回什么？ → A: 按当前确认局面重新裁定，即使已经重连或重启。原命令 ID 仍绑定原内容。已确认受理的命令原样重试时返回原回执。

- Q: 每类云端测试闭环的首次汇报应在何时发出？ → A: 首条代表性真实路径实测通过后立即汇报，并交接已验证的环境依赖。完整验收按既定成功标准执行。

- Q: 卡组文件引用的原发行版不可用，或玩家选择另一发行版时，能否导入？ → A: 可导入至选定的目标发行版。卡牌 ID 跨版本保持稳定。按目标发行版校验文件完整性和牌表合法性，缺少任一卡牌 ID 须报错。卡面和效果的版本差异无需比较。

- Q: 首版离线升级第三方前端时，谁判断新包的来源是否可信？ → A: 玩家从已安装前端的升级入口选择本地文件并确认来源，即可尝试启动兼容的同 ID 新版本。玩家负责判断来源，候选版须通过启动检查才可成为活动版本。

- Q: 第三方前端升级成功时，正在使用的旧版何时切换？ → A: 当前实例继续使用旧版及其仍有效的授权。下次打开该前端时使用新版。

- Q: 对局和状态记录如何判断可复现？ → A: 每条新记录均带版本哈希。复现前先校验版本，版本不匹配直接报错并拒绝执行。

- Q: 首版为谁交付，使用什么 AI？ → A: 首版供本项目开发者使用，暂用旧 V6 跑通工程。V6 迁移所需的隐藏信息留在可信宿主的内部试算适配器，项目跑通后再安排新模型。

- Q: 最后一条动作已确认，但结果尚未送达时应用退出，重开后如何确认胜负？ → A: 玩家从启动器打开只读终局结果或回放确认胜负。终局不重新发放行动权限，也不提供原命令回执的重试入口。
- Q: 离线回看时，谁可以读取原真人席位的私有视角？ → A: 信任本机宿主操作者。可信宿主确认操作者选择原本地真人视角，并核验归档中的原席位绑定后，授予该视角的只读回放权限。观战视角仍为公开投影。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 初始化真人对 AI 的对局 (Priority: P1)

玩家离线选择自己的卡组和 AI 对手，进入可以开始行动的对局。

**Why this priority** — 验证一场对局能连接两个不同类型的席位，并为既有玩法建立迁移基线。

**Independent Test** — 用两副合法牌表分别从 2D 和 3D 发起 PVE，检查初始化结果即可结束测试。

1. 两副牌表合法且 AI 可用时，初始化成功。玩家看到先手、公开战场和自己的起手牌，AI 收到自己席位的初始状态。先手、起手和首回合处理与旧版对应样本一致。
2. 牌表不合法或 AI 准备失败时，发起端收到原因，双方均不会收到对局就绪通知。
3. 启动器先查询并准备所选 AI 模型，通过后提交创建命令。对局层按选定版本查询并校验双方牌表、取得发行版快照，并核验和绑定预备的席位。初始化成功后，发起端取得对局引用，各连接分别取得其可见的初始视图。

4. 初始状态已确认、启动器还未收到会话引用时发生中断，玩家重开后可从正常入口找到原对局并续局。

### User Story 2 — 在 2D 使用带选择步骤的卡牌 (Priority: P1)

玩家在 2D 使用需要选择的卡牌。核心裁定使用请求、等待有权席位回应，再继续结算。双方终端按各自可见范围看到结果。

**Why this priority** — 一个用例同时覆盖命令往返、暂停恢复、结算顺序与隐藏信息。

**Independent Test** — 从固定对局状态开始，由 2D 触发待决策项，提交合法和无效应答，核对结算进度及各方可见结果。

1. 合法出牌后，仅有权选择的席位收到可选项和选择限制。该席位提交合法应答后，核心按开局锁定的规则和卡池版本恢复结算。
2. 对手和观战端收到公开结果。私有候选与牌的身份仅交付有权席位。2D、3D 或 AI 作为接收方时，对公开结果的理解一致。
3. 错误席位、无效目标或已完成的选择被拒绝。重复提交同一已处理操作不会再次结算。
4. 统一对局接口接收出牌命令，核心产生待决策项并暂停结算。接口发布可见更新。玩家随后提交另一条命令回应决策，核心恢复结算并再次向双方提供结果。

5. 玩家可从正式前端认输。核心确认胜负及原因，并保存可从启动器打开的只读结果和回放。

### User Story 3 — 编辑并保存卡组 (Priority: P2)

玩家浏览指定版本的卡池，修改卡组并保存，之后可以重新打开。

**Why this priority** — 构筑连接了玩家资产与对局准备，必须保留已有的校验和导入导出体验。

**Independent Test** — 打开一副卡组，修改后分别尝试保存合法和非法牌表，重新打开已保存记录。

1. 合法构筑保存后，重新打开可见一致的名称、卡牌数量和引用的卡池版本。
2. 校验或存储失败时，界面指出原因并保留本轮编辑，原保存记录仍可读取。
3. 从不同卡池版本进入对局时，按目标版本重新校验，并指出已移除或不符合规则的卡。
4. 打开卡组、浏览卡池或预检牌表只返回数据和校验结果。提交保存命令后由构筑服务重新校验，写入成功才返回正式卡组记录。
5. 导入另一发行版的文件时，若目标发行版含全部引用的卡牌 ID 且整副牌表合法，则以目标发行版保存，保留原名称、卡牌 ID 和数量。缺卡时指出缺失 ID 并拒绝导入。

### User Story 4 — 初始化指定的 AI 对 AI 对局 (Priority: P2)

发起者离线为两席指定卡组和模型，确认双方就绪。观战端在接入时查看公开状态。

**Why this priority** — 验证比赛流程能独立于真人前端运行，两个 AI 席位可以分别配置，首版允许两席使用各自的 V6 实例。

**Independent Test** — 配置两个 AI 席位并初始化一场 EVE，在首个模型动作之前检查两方视图和观战视图。

1. 两席配置合法时，各自收到初始席位视图，观战连接只收到公开状态。
2. 初始化完成时，系统可供确认就绪和查看初始状态。自动对战的启动和运行控制留待后续规格。
3. 任一席位初始化失败时，发起者能定位失败席位，未准备完成的会话无法进入就绪状态。
4. 两席分别准备模型。模型可用性查询返回可用信息，席位准备命令返回各席准备结果。观战者可以独立查询公开视图。

### User Story 5 — 编辑并发布新版卡池 (Priority: P2)

卡池维护者基于一个已发行版本创建草稿，编辑卡面或现有引擎支持的效果。整份草稿校验通过后可以发布。

**Why this priority** — 卡池可独立迭代，历史对局和已保存卡组仍可追溯到原版本。

**Independent Test** — 从同一版本分别提交一个缺失进化对象的草稿和一个有效改动，检查发行版本及一场已开始的对局。

1. 无效草稿不能发布，维护者能定位出错的卡牌或引用，并可继续编辑。
2. 有效草稿发布后新增可选的发行版本。已有版本仍可读取，进行中的对局继续使用开局时的内容。
3. 草稿预检返回诊断。正式发布按目标规则版本支持的触发器和效果重新校验，完整写入后才通知编辑器有新版本。

### User Story 6 — 安装并离线启动所选前端 (Priority: P1)

玩家在手机或电脑安装《临界》游戏主体，通过启动器安装官方前端或导入第三方前端包，之后可以从同一启动器离线打开。

**Why this priority** — 多端独立离线运行和前端可选安装是首版交付条件。

**Independent Test** — 在手机和电脑分别安装主体和官方 2D，导入一个第三方前端包。关闭应用和另一台设备，断网后重新启动并用第三方前端完成一次对局操作。

1. 主体提供官方 2D、3D 的单独安装入口和本地前端包导入入口。已安装前端可从列表直接打开。
2. 导入缺少必要资源、损坏或协议不兼容的包时，启动器说明原因，已有可用前端仍可打开。
3. 第三方前端只能接收玩家授权席位或公开观战的视图，并可通过协议提交该席位允许的命令。卸载只移除前端及其安装记录，游戏数据仍可由其他前端使用。
4. 断网且另一台设备关机时，当前设备仍可从冷启动打开已安装的前端并开始游戏。卡组可通过启动器导出，在另一台设备离线导入。

### User Story 7 — 在云端自主调试和验收游戏 (Priority: P1)

作为项目维护者，我希望实施代理在云端自行启动游戏、执行测试动作、读取结果并判断通过或失败，使我无需手动代点、观察界面或转交测试输出。

**Independent Test** — 在独立云端测试会话中，使用固定牌表、初始局面和随机输入，分别通过逐层测试、独立调试前端、官方 2D 和官方 3D 执行下列场景并保存可复核证据。

**Why this priority** — 云端实施代理需要能够自主验证各层与正式前端，取得维护者可复核的交付证据。

**Acceptance Scenarios**

1. **Given** 核心及相关层具备测试入口，**When** 代理独立驱动各层的业务入口，**Then** 每层均可读取结果并断言。至少验证对局结算及拒绝结果、AI 决策层产出的行动建议、构筑或卡池操作的保存或校验结果，以及玩家端的交互反馈和席位适配器提交 AI 决定的结果。
2. **Given** 自定义调试前端已获测试席位授权，**When** 代理通过适配后的指令提交动作、查询视图并响应待决策，**Then** 它可从统一玩家协议读回回执、事件和更新后的可见状态，并自行判定结果。
3. **Given** 官方 2D 或 3D 已在云端打开，**When** 代理用实际界面输入完成一局对局，**Then** 它能读取前端输出并与预期结算核对。3D 还须检查场景实际出帧、镜头表现以及卡牌和目标的拾取反馈。
4. **Given** 某类闭环的首条代表性真实路径在云端实测通过，**When** 代理取得通过证据，**Then** 代理立即向维护者汇报，随同给出可转交云空间编辑代理的环境持久化提示词，并明确提醒维护者批准将已验证的调试流程持久化为 Skill。

### Edge Cases

- 首个结算步骤就要求响应或选牌时，双方照常获得各自可见的更新。只有拥有决策权的席位可以恢复对应结算。
- 玩家基于过期状态提交动作时，收到明确结果并可以取得最新可见状态。非法或重复请求不得导致额外结算。
- 无效导入、保存失败或发布中断时，不产生部分保存的正式卡组或部分发布的正式卡池。
- 缺少匹配卡池或规则版本的历史回放须提示可辨认的原因。迁移中发现旧版已有的随机复现偏差时，单独记录其适用范围。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** — 首版必须能离线完成对局、构筑与卡池管理。重构须以仓库 [quote/](../../quote/) 内的原始 HTML 为参考。旧版 2D / 3D 游戏代码是首轮行为迁移基线，裁决书引起的规则调整在重构验收后单列。
- **FR-002** — 同一套本地会话能力必须能准备 PVE、EVE，校验牌表并固定规则版本与已发行卡池的只读快照。准备失败时须反馈原因。正在进行的对局持续使用原快照。
- **FR-003** — 核心必须是对局状态和裁定的唯一权威。出牌、攻击、回响、回合推进、随机处理、认输导致的终局及效果的等待与恢复均由核心决定。核心可以独立于前端运行。
- **FR-004** — 2D、3D、自定义客户端和 AI 适配器必须使用统一的玩家协议。协议须支持席位命令、带顺序的可见更新、当前状态、决策请求及失败反馈。各客户端可独立呈现和接收结果。层间交互须经过章程定义的层边界，按业务目的表达为 Command、Query 或 Event。Query 保持业务状态不变，Event 描述已发生的事实。同一对局协议版本内，命令、查询和事件的业务标识及含义保持稳定，兼容的客户端与核心可以独立升级。主版本不符或无共同次版本时，须报告可辨认原因并关闭连接。跨主版本兼容留待后续规划。
- **FR-005** — 对局必须按席位限定行动权及信息可见范围。观战连接只能查看公开状态。针对越权、过期、无效选择或重复命令的处理不得导致未授权结算或重复结算。
- **FR-006** — AI 玩家必须可通过独立的模型接口替换决策实现。更换模型不改变玩家协议。行动生成请求可返回受理结果，生成后的决定通知原 AI 玩家适配器，适配器再按席位提交动作。对局层须提供与正式核心同步更新的规则解算器，每次试算使用目标对局锁定的规则版本及卡池快照，只改变隔离试算状态。解算器是模型的可选能力。统一模型接口须允许依赖解算器的束搜索模型和无需解算器的模型接入，后者可根据席位观察和待决策项直接生成行动。通常试算只读取本席位可见信息，未知部分以假设补足。首版暂用旧 V6。只有可信宿主登记的 V6 内部试算适配器可在隔离副本中读取经核实为迁移所需的真实隐藏字段。须记录这些字段及受影响行为，原始数据留在该内部边界，席位适配器只接收行动意图和关联标识。新模型开发与 V6 退役在项目跑通后另行安排。
- **FR-007** — 构筑必须能按版本只读查询卡池，支持本地编辑、校验、保存、重开、导入及导出。卡组记录跨发行版稳定的卡牌 ID、数量和引用版本。开局前以选定版本重新校验。
- **FR-008** — 编辑器必须允许从发行版本创建草稿，并校验数据完整性、跨卡及预设牌表引用，以及核心对触发与效果的支持。发布必须整份成功才产生新版本。校验结果必须可定位，已发行数据保持只读。
- **FR-009** — 验收须从 `quote/` 中的 2D / 3D 行为建立可重复样本，记录样本所用的参考文件、初始条件与操作，并对比旧版和迁移版的结算顺序、关键状态及胜负。新版回放必须记录版本哈希、卡池与规则版本、动作及所需随机结果。无法复现的旧版场景及原因单独记录。单列 V6 的隐藏信息依赖、受影响样本及可观察决策差异，核心规则与结算仍按旧版基线验收。
- **FR-010** — 本地程序正常退出或异常中断后，须直接载入最近一次确认的权威状态以恢复未结束的对局，继续使用原规则版本及卡池快照。恢复范围包括席位绑定、权威对局状态、结算进度、待决策项、命令 ID 和原内容的绑定，以及已确认受理的命令结果。确认回执及其对局影响须一致。在未结束的对局中，原授权席位在同一会话内重新接入或重启恢复后，原样重试已确认受理的命令须取得原回执，且结算最多发生一次。创建提交成功但启动器尚未收到会话引用时若发生中断，重启后须能从启动器找到已确认的原对局并续局。通过授权但因规则被拒绝的命令，原样重试时按当前确认局面重新裁定。同一命令标识在首次通过授权并经规则裁定后须绑定原内容，重连或重启后更换内容仍须拒绝。动作和 AI 决定仅在对应对局、席位以及原行动或决策仍有效时受理。恢复须保留已确认待决策的原 ID、候选和结算位置，随机候选不得重新抽样。恢复后只向有权接入的席位提供各自可见的结果。续局前须校验最近确认记录的版本哈希。原规则或卡池版本不可用、版本哈希不匹配，或最近确认记录不完整时，须阻止续局并报告对应原因，保留已有记录。
- **FR-011** — 对局层须保留完整、有序的对局日志及足以恢复每个已确认历史状态的状态记录。每条新对局日志、状态快照、持久化命令记录和回放记录均须写入开局锁定的版本哈希。日志、状态记录和对应的规则版本及卡池快照须足以在独立的复现环境中重建选定的中间状态，并使用原输入复现后续行为。复现过程与正式对局隔离，原对局的当前进度、命令处理结果和历史记录保持原样。仅可信宿主内获准的项目开发者和隔离自动验收可以发起历史复现。普通席位和观战端继续按业务角色接收各自的投影视图。执行前须把本次使用的全部记录的哈希与加载的规则和卡池版本哈希比较。版本不匹配须直接报告版本错误并拒绝执行。缺少确认点、匹配版本不可用或记录不完整时分别报告对应原因。完整候选与原随机输入仅限获准的内部复现读取。席位只获取自己的可见结果及仍有权响应的候选，观战端只获取公开结果。玩家须能从启动器的正常入口打开已确认的只读终局结果或回放，包括最后一步已确认但结果或回执尚未送达即退出的情况。终局结果以已确认记录为准，回放执行前须校验版本哈希和记录完整性。终局后终止对局行动授权，原命令回执不再通过玩家接口重试领取。公开视角只展示公开结果。可信宿主确认本机操作者选择原本地真人视角，并核验归档中的原席位绑定后，可离线授予该回放的只读权限，展示原真人席位当时有权看到的内容。该授权不适用于 AI 席位，也不包含完整候选流、原随机输入或开发诊断。可信宿主为获准开发者提供带版本哈希的诊断记录导出，用于项目内分析和复现。该入口与前端协议隔离。
- **FR-012** — 卡牌效果优先用对局核心支持的通用规则步骤组合表达，核心统一负责触发、选择、结算与暂停恢复。若现有通用步骤及其参数无法复现旧版样本的触发时机或次数、应答席位与暂停恢复、结算依赖或顺序，且保留行为需要为卡名开特例、由前端代裁定或破坏核心不变量，即达到批量重构条件。须记录触发差异的样本和影响范围，设计统一的效果抽象，并批量迁移卡池内所有依赖受影响结构的效果。重构应遵循 FR-001 的旧版行为基线，发布前按目标规则版本验证整份卡池。

- **FR-013** — 手机和电脑均可独立安装游戏主体。完成首次安装和前端准备后，应能独立离线冷启动、开局、构筑和管理卡池。首次准备须在空存储中提供已校验、可随主体离线使用的官方卡池发行版及预设牌表。发行版固定规则版本，卡牌及预设引用沿用可追溯的旧版数据和稳定 ID 映射。首次准备中断后可重试，只能产生一个完整的初始发行版。
- **FR-014** — 启动器须支持单独安装官方 2D、3D，以及从本地文件安装和卸载第三方前端。安装须检查包及协议兼容性，区分资源缺失、包损坏、版本不兼容、ID 冲突和空间或配额不足。启动器须为已安装的第三方前端提供离线升级入口。玩家选择兼容的同 ID 新版本并确认文件来源后，宿主可启动候选实例。首次导入和升级的候选版均须通过启动检查才可成为活动版本。升级成功后，下次打开该前端时使用新版。已运行的旧实例继续使用原版本及其仍有效的授权，当前对局可以继续操作。首次导入失败后可从新装入口重新尝试。通过新装入口导入已安装 ID 的包须报告冲突。第三方前端通过授权玩家协议运行，安装失败及卸载不得损坏既有游戏数据。
- **FR-015** — 各设备独立保存卡组，通过本地文件导入导出完成跨设备迁移。新版文件保留名称、发行版 ID、稳定卡牌 ID 和数量。导入按所选目标发行版校验文件完整性和整副牌表合法性，原发行版可不在目标设备。每张牌须凭同一卡牌 ID 在目标发行版找到，无需比较卡面和效果。缺卡时须报告缺失 ID 和目标发行版并拒绝导入。成功后以目标发行版保存名称、卡牌 ID 和数量。原文件不变，失败不产生部分记录或修改既有卡组。旧格式以可定位的旧文件样本及稳定 ID 映射确定兼容范围。

- **FR-016** — 云端测试须支持在隔离环境中自主准备样本、执行动作、读取输出、断言结果和保存复现证据。逐层闭环须通过章程定义的四层各自的正常业务入口独立验证其职责，从输入到可观察结果再到断言。失败用例须验证拒绝原因及相关业务不变量，例如非法动作未改变局面、失败的保存未留下部分记录。自定义调试前端须通过统一玩家协议将测试指令映射为席位操作，读取授权视图、命令回执、待决策和可见事件。规则与卡池版本、牌表、初始状态和随机输入由隔离的测试环境固定。调试前端依据读回的授权视图、回执和待决策项推动后续操作，并遵循正式席位授权与可见性。
- **FR-017** — 官方 2D 和 3D 须分别支持云端端到端测试，从启动、开局、换牌、出牌或攻击、响应待决策到终局均可由代理自行执行和检查。官方前端验收须通过真实界面输入验证，并从界面直接验证至少一次操作反馈及终局显示，以对应的回执、事件或回放核对权威结算。3D 须覆盖实际出帧、既有固定机位下的镜头表现、卡牌和目标拾取。证据须包含场景输入、操作顺序、断言结果和足以定位失败的界面或对局记录。渲染不可用、输出缺失或断言失败的场景须记录具体阻塞及证据，待实测通过后再计入通过范围。
- **FR-018** — 实施代理须在逐层测试、调试前端、官方 2D 和官方 3D 各自首条代表性真实路径实测跑通时，立即在继续后续实施前向维护者汇报。代表性路径须从该类闭环的正常入口执行实际操作、读回结果并通过断言。四类首条路径的断言见[验收指南](quickstart.md#证据首次通过与交接)。汇报须包含已通过的范围、尚待执行的验收、复现入口及证据，并随同交付一份可直接转交云空间编辑代理的提示词。提示词须逐项说明为了跑通哪个闭环环节实际新增或调整了哪项依赖或环境配置、所用版本或约束、用途、持久化配置位置或安装方式，以及如何在新会话验证其有效。也要说明该环节若无新增依赖，如何用现有环境复验。提示词须明确请求把上述环境改动保留为后续云会话的持久化基础。新会话复验是环境交接步骤，首次汇报在当前会话取得相应证据时发出。实施代理须在同一汇报中提醒维护者批准将已验证的调试与复现流程制作成持久化 Skill，并在得到明确批准后再制作。发出带审批提醒的汇报后，可继续与 Skill 制作无关的实施。

### Key Entities

- **对局会话、席位与视图** — 本地会话维护席位绑定、控制者与就绪状态。核心持有权威对局状态及开局快照。对局接口按连接投影可见视图，客户端保存视图副本。
- **玩家命令、待决策项与结算结果** — 动作意图、应答席位、候选与限制、公开或私有的有序更新，以及拒绝结果。待决策项和恢复位置由核心持有，对局接口提供相应席位可见的部分。
- **AI 配置与决定** — AI 玩家适配器负责席位上下文及待提交决定。AI 决策层负责模型自身的决策上下文与隔离试算状态。对局层负责正式规则解算器及其版本一致性。模型可按需调用解算器，也可直接从席位观察和待决策项生成行动。
- **卡牌、已发行卡池与草稿** — 稳定卡牌标识、版本化卡面与效果、草稿与基础发行版本的关系。
- **用户卡组** — 本地保存的牌表、名称和卡池版本。
- **对局恢复记录** — 对局层保有用于重启的最近一次确认状态，以及用于独立复现指定中间状态的完整对局日志、状态记录与版本资源。正式对局续局后由对局接口按席位重新提供可见视图。
- **回放记录** — 支撑复现的卡池及规则版本、动作、随机输入或结果。

- **前端包、安装记录与连接授权** — 启动器管理前端包的兼容性、安装状态与运行实例。对局接口负责授权连接并限定其视图和命令范围。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** — 断网状态下，PVE、EVE、构筑保存、2D 出牌及卡池发布五类场景各通过至少一条成功用例和一条失败用例。
- **SC-002** — 纳入迁移验收的旧版样本在相同初始状态、动作和随机输入下，关键状态、结算顺序及胜负须一致。LG-06 的无效应答分支按旧版与迁移版各自的断言验收，迁移版须拒绝并保留原暂停点。样本至少覆盖开局与换牌、出牌、攻击、进化、技能、回响、终焉、百川冰泉和认输。各场景的固定样本和断言见[旧版对照样本](contracts/legacy-samples.md)。
- **SC-003** — 用 2D、3D、独立的测试客户端和 AI 模型适配器各验证至少一次协议接入。另用独立测试客户端分别验证客户端单独更新和核心单独更新后，同一协议版本内既有命令、查询和事件仍可按原业务含义交互。用涉及私有牌区的待决策样本验证合法应答与错误应答，对手和观战视图中未获授权的候选和牌身份泄露为零。用含对手手牌和未抽牌顺序的样本验证，只有登记的 V6 内部试算适配器可读所需真实隐藏字段。席位适配器、未获准模型和观战连接均无法读到这类试算资料。
- **SC-004** — 同一场对局跨一次卡池发布后依旧使用原版本。至少两次发布验证分别覆盖有效改动和无效引用，前者只新增一个版本，后者新增零个版本。保存后的合法卡组重新打开时名称、牌表和版本一致。
- **SC-005** — 至少一份含随机结算的新版回放，在匹配版本下重放至同一终局。另验证缺少匹配版本以及版本标识相同但哈希不同的记录均被拒绝，规则执行尚未开始。验证获准开发者导出的诊断记录保留版本哈希，玩家协议连接无法调用该入口。另在致胜命令确认后、回执与结果送达前退出。断网重开，以一个兼容的新装前端从启动器打开同一局的结果或回放，核对胜负及其原因，旧行动端口和最后一条命令的回执均不可重新取得。分别验证公开视角、经宿主确认的原真人视角，以及未确认或请求 AI 席位时的访问限制。
- **SC-006** — 用含待决策的样本验证三个恢复场景。界面在命令已处理但未收到回复时断开，重新接入并重试须取得原结果。程序在等待选择时退出，重启后原有权席位可继续选择。程序在应答结果已确认但尚未回复时异常退出，重启后重试须取得原结果，受影响的牌区与其他局面保持在确认后的状态。另验证创建已确认但会话引用尚未送达时退出，重开后启动器能找到并恢复同一未结束对局，且只存在一场已确认的对局。另验证针对已失效选择的迟到 AI 决定在恢复后被拒绝，且对局状态无变化。用「探珠」验证随机候选确认后退出，续局可用原决策 ID 选择同一候选集，随机抽样次数保持不变。用缺版本、版本哈希不匹配和不完整记录检查续局诊断。另验证已获授权的席位在原待决策中提交无效选项、再用新命令合法完成选择。重启后原样重试第一条命令须返回决策失效，同 ID 更换内容须返回冲突。
- **SC-007** — 对一场包含暂停选择和随机结算的样本，在独立的复现环境中逐一重建从开局到结算结束每个已确认的历史状态，核对原规则和卡池版本、局面、结算进度、待决策项及截至该点的命令处理结果。从等待选择的中间状态重放原选择及所需随机输入，核对后续结算顺序和结果，并验证复现前后原对局的当前进度、命令处理结果和历史记录一致。逐条核对被使用的对局日志、确认状态和命令记录均带开局版本哈希。分别验证未授权访问、缺少确认点、版本哈希不匹配及记录不完整的诊断。版本标识相同但哈希不同的样本也必须在执行前被拒绝。
- **SC-008** — 用含选择和条件分支的多步样本验证通用步骤能表达触发、暂停、恢复和结算顺序。若触发卡牌效果的批量重构，则须记录受影响卡牌与对应的旧版效果结构，并以迁移样本对照触发、选择、结算顺序及结果。整份卡池通过目标规则版本的发布校验。
- **SC-009** — 以旧 V6 完成离线对局。用同一规则版本、卡池快照、初始状态、动作和随机输入，比对正式解算器在隔离副本中的结算顺序与结果，确认正式对局在试算前后保持一致。以无需解算器的测试替身验证同一模型接口可接收观察和待决策项，并经席位命令提交行动。

- **SC-010** — 至少在一部 iOS 手机、一部 Android 手机和一台电脑从空存储分别安装主体并准备所选前端。完全关闭应用、断开当前设备网络并关闭另一台设备后，从安装图标冷启动。通过正常入口打开初始官方发行版、使用预设牌表开局并基于该版创建草稿。另验证首次准备中断后重试只得到一个完整发行版。三类设备分别验证第三方包离线导入和独立开局，官方 2D 与 3D 在手机用触控、桌面用鼠标执行对局操作，3D 另验证实际出帧、镜头和拾取。逐设备记录机型、系统、浏览器、安装及断网状态、输入和 3D 表现及复现步骤。空存储验收步骤见[验收指南](quickstart.md#首次发行版与空存储验收)，桌面浏览器云端验收的范围和证据见 SC-013。
- **SC-011** — 用资源缺失、损坏、不兼容、ID 冲突及空间不足样本分别验证导入失败反馈，并模拟写入配额失败。断网验证玩家从升级入口选取同 ID 新版本并确认来源后可升级，取消确认时旧版保持活动，从新装入口导入该文件时须报告 ID 冲突。用旧版正在等待玩家选择的对局验证，升级成功后旧实例仍能提交该选择。关闭旧实例后再次打开该前端，须启动新版并按正常流程重新授权。用候选版启动失败样本分别验证初装和升级。初装失败后原 ID 可重新导入。升级失败后上一活动版本及既有授权可用。两种情况的失败候选端口均须撤销。测试第三方包只能得到授权视图，卸载后原卡组和回放仍可打开。在断网手机上验证电脑导出卡组的同版本与跨版本导入。同版本保持名称、牌表及发行版。跨版本时，有相同卡牌 ID 的卡面或效果变化仍可通过校验，保存名称、牌表及所选目标发行版。缺卡、文件不完整或牌表不符合目标构筑规则时须报告原因，且不写入部分记录。

- **SC-012** — 在云端以零次维护者手工操作，通过四层各至少一条成功用例和一条失败用例。独立调试前端至少完成一次含待决策项的指令往返，核对回执、有序可见事件及结算状态，并验证一次非法或越权指令未改变对局。
- **SC-013** — 官方 2D 和 3D 各至少自主完成一场从开局到终局的云端对局，覆盖 FR-017 所列操作。在相同规则和卡池版本、初始局面及随机输入下，固定双方牌表，通过调试前端、2D 和 3D 各执行一次同一固定场景的等价游戏动作。动作等价指同一逻辑席位在同一确认进度提交相同业务意图、目标和决策选项。对各端临时 ID 作同一场景的逻辑映射，再核对相同授权范围内的关键状态、结算顺序和结果一致。3D 另有出帧、镜头表现与拾取成功的界面证据。
- **SC-014** — 每类闭环的首条代表性真实路径通过时，均有当时发出的汇报和可转交提示词。完整验收另按 SC-012 和 SC-013 核对。可逐项从提示词追溯实际环境改动到对应闭环环节及复验方式，并可核对汇报包含 Skill 持久化审批提醒。

## Assumptions

- 正式卡组保存首版按既有构筑器校验口径。未完成卡组的持久化草稿仍待讨论。
- PVE 默认沿用旧版真人先手。EVE 首轮验收停在初始化，自动对战的运行控制、观战界面范围留待细化。
- SQLite 卡池为章程约束。首版跨设备通过文件传递卡组。旧卡组和旧回放兼容边界由实现计划和旧版实测样本确定。
- 云端自主验收覆盖桌面浏览器与可在云端运行的各层测试。iOS、Android 的安装、离线冷启动、触控及设备能力继续按既有实机要求验收。
