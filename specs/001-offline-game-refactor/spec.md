- [ ] **CL-01 · 缺乏交互的稳定身份**

  **问题** — 同一种跨层交互要在哪些范围内保持可识别，重复命令和迟到的 AI 决定又应如何关联到原请求？

  **完成标准** — 约定交互类型的身份及兼容范围，并明确命令、事件、待决策项、AI 决定各自的作用域和关联。能从两端边界追踪同一项交互，验收可区分同一命令的重试、新命令和已失效决定。
- [ ] **CL-02 · 状态所有权还需要进一步细化**

  **问题** — 每项状态由谁唯一写入，哪些席位或模块可读取，何时有效或失效？

  **完成标准** — 对席位绑定、权威对局状态、待结算进度、席位投影、模型及试算上下文、用户卡组和发行版逐项确定写入者、读取权限和生命周期。标明哪些是权威记录、哪些是副本，以及旧 V6 试算可读取的具体范围。
- [ ] **CL-03 · 缺乏业务不变量和禁止性约束**

  **问题** — 哪些状态在每次业务交互后都必须成立，哪些行为必须被拒绝或回滚？

  **完成标准** — 按场景列出行动权、隐藏信息、重复结算、隔离试算、快照固定、发布原子性的约束、裁定方及失败后仍成立的状态。每条已确认约束有一个可验证的反例，并注明与旧版已知行为偏差的关系。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 初始化真人对 AI 的对局 (Priority: P1)

玩家离线选择自己的卡组和 AI 对手，进入可以开始行动的对局。

**Why this priority** — 验证一场对局能连接两个不同类型的席位，并为既有玩法建立迁移基线。

**Independent Test** — 用两副合法牌表分别从 2D 和 3D 发起 PVE，检查初始化结果即可结束测试。

1. 两副牌表合法且 AI 可用时，初始化成功。玩家看到先手、公开战场和自己的起手牌，AI 收到自己席位的初始状态。先手、起手和首回合处理与旧版对应样本一致。
2. 牌表不合法或 AI 准备失败时，发起端收到原因，双方均不会收到对局就绪通知。
3. 发起端提交创建命令。对局层按选定版本查询并校验双方牌表、取得发行版快照、准备席位。初始化成功后，发起端取得对局引用，各连接分别取得其可见的初始视图。

### User Story 2 — 在 2D 使用带选择步骤的卡牌 (Priority: P1)

玩家在 2D 使用「炽羽」。核心裁定使用请求、等待玩家选弃牌，再继续结算。双方终端按各自可见范围看到结果。

**Why this priority** — 一个用例同时覆盖命令往返、暂停恢复、结算顺序与隐藏信息。

**Independent Test** — 从固定对局状态开始，由 2D 使用「炽羽」，分别以朱雀牌和非朱雀牌完成弃牌选择。

1. 合法出牌后，仅有权选择的席位收到可选项和选择限制。该席位完成合法弃牌后，核心按旧版规则抽两张，并在弃掉朱雀牌时追加一张。
2. 对方收到公开弃牌和抽牌数量。新抽牌的身份只在持有者可见范围内交付。2D、3D 或 AI 作为接收方时，对公开结果的理解一致。
3. 错误席位、无效目标或已完成的选择被拒绝。重复提交同一已处理操作不会再次结算。
4. 统一对局接口接收出牌命令，核心产生待决策项并暂停结算。接口发布可见更新。玩家随后提交另一条命令回应决策，核心恢复结算并再次向双方提供结果。

### User Story 3 — 编辑并保存卡组 (Priority: P2)

玩家浏览指定版本的卡池，修改卡组并保存，之后可以重新打开。

**Why this priority** — 构筑连接了玩家资产与对局准备，必须保留已有的校验和导入导出体验。

**Independent Test** — 打开一副卡组，修改后分别尝试保存合法和非法牌表，重新打开已保存记录。

1. 合法构筑保存后，重新打开可见一致的名称、卡牌数量和引用的卡池版本。
2. 校验或存储失败时，界面指出原因并保留本轮编辑，原保存记录仍可读取。
3. 从不同卡池版本进入对局时，按目标版本重新校验，并指出已移除或不符合规则的卡。
4. 打开卡组、浏览卡池或预检牌表只返回数据和校验结果。提交保存命令后由构筑服务重新校验，写入成功才返回正式卡组记录。

### User Story 4 — 初始化指定的 AI 对 AI 对局 (Priority: P2)

发起者离线为两席指定卡组和模型，确认双方就绪。观战端在接入时查看公开状态。

**Why this priority** — 验证比赛流程能独立于真人前端运行，两个 AI 模型可以分别配置。

**Independent Test** — 配置两个 AI 席位并初始化一场 EVE，在首个模型动作之前检查两方视图和观战视图。

1. 两席配置合法时，各自收到初始席位视图，观战连接只收到公开状态。
2. 初始化完成时，系统可供确认就绪和查看初始状态。自动对战在另行启动后执行。
3. 任一席位初始化失败时，发起者能定位失败席位，未准备完成的会话无法进入就绪状态。
4. 两席分别准备模型。模型可用性查询返回可用信息，席位准备命令返回各席准备结果。观战者可以独立查询公开视图。

### User Story 5 — 编辑并发布新版卡池 (Priority: P2)

卡池维护者基于一个已发行版本创建草稿，编辑卡面或现有引擎支持的效果。整份草稿校验通过后可以发布。

**Why this priority** — 卡池可独立迭代，历史对局和已保存卡组仍可追溯到原版本。

**Independent Test** — 从同一版本分别提交一个缺失进化对象的草稿和一个有效改动，检查发行版本及一场已开始的对局。

1. 无效草稿不能发布，维护者能定位出错的卡牌或引用，并可继续编辑。
2. 有效草稿发布后新增可选的发行版本。已有版本仍可读取，进行中的对局继续使用开局时的内容。
3. 草稿预检返回诊断。正式发布按目标规则版本支持的触发器和效果重新校验，完整写入后才通知编辑器有新版本。

### Edge Cases

- 首个结算步骤就要求响应或选牌时，双方照常获得各自可见的更新。只有拥有决策权的席位可以恢复对应结算。
- 玩家基于过期状态提交动作时，收到明确结果并可以取得最新可见状态。非法或重复请求不得导致额外结算。
- 无效导入、保存失败或发布中断时，不产生部分保存的正式卡组或部分发布的正式卡池。
- 缺少匹配卡池或规则版本的历史回放须提示可辨认的原因。迁移中发现旧版已有的随机复现偏差时，单独记录其适用范围。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** — 首版必须能离线完成对局、构筑与卡池管理。重构须以仓库 [quote/](../../quote/) 内的原始 HTML 为参考。旧版 2D / 3D 游戏代码是首轮行为迁移基线，裁决书引起的规则调整在重构验收后单列。
- **FR-002** — 同一套本地会话能力必须能准备 PVE、EVE，校验牌表并固定规则版本与已发行卡池的只读快照。准备失败时须反馈原因。正在进行的对局持续使用原快照。
- **FR-003** — 核心必须是对局状态和裁定的唯一权威。出牌、攻击、回响、回合推进、随机处理及效果的等待与恢复均由核心决定。核心可以独立于前端运行。
- **FR-004** — 2D、3D、自定义客户端和 AI 适配器必须使用统一的玩家协议。协议须支持席位命令、带顺序的可见更新、当前状态、决策请求及失败反馈。各客户端可独立呈现和接收结果。层间交互须经过章程定义的层边界，按业务目的表达为 Command、Query 或 Event。Query 保持业务状态不变，Event 描述已发生的事实。
- **FR-005** — 对局必须按席位限定行动权及信息可见范围。观战连接只能查看公开状态。针对越权、过期、无效选择或重复命令的处理不得导致未授权结算或重复结算。
- **FR-006** — AI 玩家必须可通过独立的模型接口替换决策实现。更换模型不改变玩家协议。行动生成请求可返回受理结果，生成后的决定通知原 AI 玩家适配器，适配器再按席位提交动作。试算只改变隔离副本。迁移旧 V6 时，其兼容试算所需的内部数据与公开席位视图隔离。
- **FR-007** — 构筑必须能按版本只读查询卡池，支持本地编辑、校验、保存、重开、导入及导出。卡组记录稳定卡牌标识、数量和引用版本。开局前以选定版本重新校验。
- **FR-008** — 编辑器必须允许从发行版本创建草稿，并校验数据完整性、跨卡及预设牌表引用，以及核心对触发与效果的支持。发布必须整份成功才产生新版本。校验结果必须可定位，已发行数据保持只读。
- **FR-009** — 验收须从 `quote/` 中的 2D / 3D 行为建立可重复样本，记录样本所用的参考文件、初始条件与操作，并对比旧版和迁移版的结算顺序、关键状态及胜负。新版回放必须记录卡池与规则版本、动作及所需随机结果。无法复现的旧版场景及原因单独记录。

### Key Entities

- **对局会话、席位与视图** — 本地会话维护席位绑定、控制者与就绪状态。核心持有权威对局状态及开局快照。对局接口按连接投影可见视图，客户端保存视图副本。
- **玩家命令、待决策项与结算结果** — 动作意图、应答席位、候选与限制、公开或私有的有序更新，以及拒绝结果。待决策项和恢复位置由核心持有，对局接口提供相应席位可见的部分。
- **AI 配置与决定** — AI 玩家适配器负责席位上下文及待提交决定。AI 决策层负责模型自身的决策上下文与隔离试算状态。
- **卡牌、已发行卡池与草稿** — 稳定卡牌标识、版本化卡面与效果、草稿与基础发行版本的关系。
- **用户卡组** — 本地保存的牌表、名称和卡池版本。
- **回放记录** — 支撑复现的卡池及规则版本、动作、随机输入或结果。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** — 断网状态下，PVE、EVE、构筑保存、2D 出牌及卡池发布五类场景各通过至少一条成功用例和一条失败用例。
- **SC-002** — 所有纳入迁移验收的旧版样本在相同初始状态、动作和随机输入下，关键状态、结算顺序及胜负一致。样本至少覆盖开局与换牌、出牌与攻击、回响、终焉和百川冰泉。
- **SC-003** — 用 2D、3D、独立的测试客户端和 AI 模型适配器各验证至少一次协议接入。两条「炽羽」样本分别验证追加抽牌与普通抽牌，且对手及观战视图中公开范围之外的手牌身份泄露为零。
- **SC-004** — 同一场对局跨一次卡池发布后依旧使用原版本。至少两次发布验证分别覆盖有效改动和无效引用，前者只新增一个版本，后者新增零个版本。保存后的合法卡组重新打开时名称、牌表和版本一致。
- **SC-005** — 至少一份含随机结算的新版回放，在匹配版本下重放至同一终局。至少一份缺少匹配版本的回放能明确报告原因。

## Assumptions

- 正式卡组保存首版按既有构筑器校验口径。未完成卡组的持久化草稿仍待讨论。
- PVE 默认沿用旧版真人先手。EVE 首轮验收停在初始化，自动对战的运行控制、观战界面范围留待细化。
- SQLite 卡池是已确认的章程约束。单 HTML 或本地应用、运行与打包方式、账号与同步范围、旧卡组和旧回放的具体兼容范围留待后续讨论。
