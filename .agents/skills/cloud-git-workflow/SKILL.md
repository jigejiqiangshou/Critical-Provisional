# Git 云环境启动同步与分支管理协议

## 1. 确认适用范围

先根据实际运行与开发环境判断本协议是否生效。项目使用 Git、关联 GitHub 或通过 Codex 开发，均不足以判定它属于 Codex 云环境。

- **Codex 云环境开发**：在分析项目、读取业务代码、制定开发计划或修改文件之前，完成并验证启动同步。
- **本地开发**：根据用户指令和项目开发规范处理 Git 操作。本协议不触发拉取、分支切换或版本同步。
- **环境类型无法确认**：暂停本协议中的 Git 同步操作。

## 2. 启动同步

GitHub 远程仓库是项目版本的唯一权威来源。默认使用最新的 `origin/work` 作为基线，在本地 `work` 分支开发。用户明确指定分支、Commit 或 Tag 时，使用指定基线。`main` 是主分支，向 `main` 提交或推送须有用户明确指令。

1. 检查当前 Git 仓库、远程地址、工作区和暂存区状态、当前分支及 `HEAD`。检查 Git 版本及所需操作是否可用。
2. 执行 `git fetch --all --prune`。检查远程的目标分支是否存在，并确认其最新提交已获取。如果远程仅配置了部分分支的 fetch refspec，显式获取目标远程分支，再核实对应远程跟踪引用的提交。
3. 比较本地目标分支和远程目标分支的独有提交。默认同步至 `origin/work`，进入本地 `work` 并确认跟踪关系。本地没有 `work` 且远程有 `origin/work` 时，从最新 `origin/work` 创建本地 `work` 并建立跟踪关系。本地分支仅落后时，优先快进同步。
4. 同步和切换前，保护已有的未提交修改、本地独有提交及其他分支的成果。遇到分叉或潜在冲突，先判断是否能在保留成果和既定意图的前提下安全同步。
5. 验证当前分支或指定版本、实际 `HEAD` 及目标基线。确认无误后再开始开发。

远程没有 `work` 且用户未指定其他基线时，暂停开发并报告。不得自动改用 `main`，也不得自动创建或推送远程 `work`。远程无法访问、获取失败或无法确认基线为最新版本时，先尝试授权范围内的安全恢复。仍无法验证时，暂停开发并报告阻塞。

## 3. 开发分支、提交与推送

- 默认在 `work` 开发及提交，推送目标为 `origin/work`。用户明确指定其他开发分支时，在该分支开发、提交并推送到对应目标。用户通过 Commit 或 Tag 指定基线时，保留该基线，按明确的目标分支完成后续提交与推送。
- 提交前确认当前分支符合任务要求，检查远程是否出现新提交。远程有更新时先安全同步，再提交和推送。默认推送使用 `git push origin work`。
- `work` 合并至 `main` 应遵循用户明确指定的合并流程。未经授权，不执行破坏性重置、强制推送、历史重写或删除包含未合并成果的分支。
- 用户要求独立分支或多 Agent 并行开发时，默认从最新 `origin/work` 创建独立分支，各 Agent 在自己的分支开发和提交。仅在用户明确要求时进行分支合并、变基或其他集成。其他 Agent 尚未合并的分支不得自动成为正式开发基线。

## 4. 验证与异常报告

自主完成版本检查、同步和分支确认。完成提交和推送后，验证相关提交已出现在预期的远程分支，并核对本地与远程状态。正常情况下只需简要报告基线同步和提交推送结果。本地开发无需报告本协议的适用情况。

对可在授权范围内解决的同步问题，自主修复并复验。无法安全保留现有成果、无法确认基线、推送失败或需要用户决定时，报告具体阻塞及影响。
