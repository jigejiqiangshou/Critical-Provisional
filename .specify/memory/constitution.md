# 《临界》项目章程

## 核心原则

### I. 离线运行与现有行为基线

首版的对局、构筑和卡池管理必须可在离线环境中完成。工程化重构以现有 2D 和 3D
游戏代码的可观察行为为验收基线。迁移期间发现的行为差异必须记录，并通过旧版运行
或源码确认其来源。裁决书驱动的规则调整在重构验收后单独立项、验证和发布。

### II. 由核心统一裁定对局

对局核心拥有权威状态，负责动作合法性、回合推进、响应窗口、随机处理和效果结算。
核心必须能够脱离界面运行。需要输入时，由核心保留待决策项和结算进度，并验证决定
来自有权行动的席位。界面和 AI 通过提交命令推动对局。

### III. 共用玩家协议与独立实现

2D、3D、自定义前端及 AI 玩家适配器必须使用同一份对局协议提交命令并接收结果。
协议必须定义席位可见状态、待决策项、可见事件、更新顺序及拒绝原因。
前端独立实现渲染和交互。AI 玩家适配器通过独立的模型接口调用决策实现，
更换模型无须修改对局协议。迁移现有 V6 所需的内部试算能力必须留在内部适配器中，
并与公开席位接口的可见性边界隔离。

### IV. 卡池只读快照与版本化发布

SQLite 统一管理卡牌库和已发行版本。构筑服务通过卡牌目录只读查询卡牌库，
用户卡组由用户数据存储独立管理。对局初始化时必须固定卡池只读快照和规则版本。

卡牌编辑器从已发行快照创建可编辑草稿。发布前必须校验整份草稿的数据完整性、
跨卡引用和规则核心支持的触发器及效果。通过校验后，以事务新增一个不可变的发行
版本。既有发行版本必须保持可追溯，已开始的对局继续使用原快照。

### V. 可验证的迁移与可追溯的结算

触及对局行为的迁移必须有可重复的验收样本。使用一致的初始状态、随机输入和玩家
命令，比较旧版与迁移版的结算顺序、关键状态及胜负。回放应记录支撑复现的卡池及规则
版本、动作与随机结果。旧版回放已经存在的复现限制必须单独记录。

### VI. 层级是最高架构抽象

项目必须先按业务职责和状态所有权划分层，再在层内划分模块。设计、实现与评审以
本章程定义的四层及其对外契约为准。新增职责须优先由已有层和模块承接。只有四层
均无法承接明确职责时，才可提出层级调整，并按章程治理流程说明理由和影响。

## 架构与数据边界

### 层级分类

| 层 | 职责 | 关键状态归属 | 对外能力 |
|---|---|---|---|
| 玩家端与观战端层 | 2D、3D、自定义前端实现交互。AI 玩家适配器接收席位任务并提交模型决定。观战端展示公开信息。 | 界面交互、客户端视图副本、AI 适配器的席位上下文与待提交决定。 | 发起对局和构筑操作，准备 AI 席位，提交动作，查询视图并接收更新。 |
| 对局层 | 本地会话组装并初始化对局。核心负责裁定与暂停恢复。统一对局接口核验席位、投影视图并分发有序更新。回放模块记录对局。 | 会话持有席位绑定和就绪状态。核心持有权威对局状态、固定卡池快照和待决策项。接口持有已投影视图及更新顺序。回放模块持有回放记录。 | 创建和初始化对局，接收玩家命令，提供席位及观战视图，发布可见事件，并提供经过授权的只读试算资料和指定规则版本的能力说明。 |
| AI 决策层 | 统一模型接口，根据观察和待决策项生成行动建议，按需提供隔离试算。 | 模型的决策上下文与隔离试算状态。 | 受理生成行动的请求，通知行动已生成。试算只读获取授权资料，模拟变化仅发生于隔离副本。 |
| 构筑与卡池层 | 构筑服务查询和校验牌表，用户卡组存储负责持久化。卡牌目录提供版本查询，编辑器和发布模块负责草稿与发行。 | 用户卡组、编辑草稿、SQLite 中的不可变卡池发行版本。 | 打开、校验和保存构筑，提供指定发行版本的只读快照，预检草稿并发布新版本。 |

### 层与模块的边界

- 层级总图每层一个节点，仅展示层间业务交互。每条边必须给出方向、语义和具体业务
  含义。同向且同语义的交互可合并。用关键场景检查请求入口、数据来源、返回或通知，
  以及接收方发起的后续交互。
- 每张层内 Mermaid flowchart 用一个 `subgraph` 表示该层，子图内是实际模块。模块
  必须明确职责及状态归属，包括裁定、存储、视图投影和请求处理。新增模块或抽象须
  说明职责、对应场景及待确认的决定。
- 每张层内图必须在 `subgraph` 外绘制一个「层边界」节点，表示本层对外契约。
  外部进入本层的边从层边界指向接收模块，向外的边从发起模块指向层边界。层内协作
  直接连线。总图中每项跨层交互在两端层内图都必须可追踪，方向、语义和业务含义一致。

### 统一交互语义

业务连线必须使用 `语义 · 业务含义`，仅允许如下三类。

| 语义 | 业务含义与方向 |
|---|---|
| Command | 请求其他模块执行行为，可能改变状态，箭头从请求方指向执行方。 |
| Query | 读取或计算信息，业务状态保持不变，箭头从请求方指向提供方。 |
| Event | 通知其他模块某个事实已发生，箭头从发布方指向接收方。 |

命令的受理或拒绝、查询的数据结果沿原交互返回。事件可与命令受理并存，接收方可以
独立发起后续命令或查询。交互语义先由业务目的确定，传输方式在实现阶段选择。

### 业务约束

- 本地对局会话负责组装牌表、快照、席位和玩家适配器。PVE 与 EVE 共用核心初始化
  与对局协议，席位控制者由会话层配置。观战接入时使用公开视图。
- 构筑服务负责查询、编辑校验、保存及导入导出。进入对局前须按所选卡池版本校验牌表。
  跨版本引用使用稳定卡牌 ID，旧卡组兼容范围在对应规格中明确。
- 对局运行形态保持离线。单 HTML 或本地应用的交付方式，以及账户、同步和分享的范围，
  由后续规格确定。

## 规格与验收

- 规格必须指出受影响的模块边界、可见性和兼容范围。实现计划的 Constitution Check
  必须说明相关原则如何得到满足，并为行为变化提供可检查的验收依据。
- 涉及对局接口时，验收应覆盖 PVE 与 EVE 初始化、席位视图和一次需暂停后恢复的
  出牌结算。涉及构筑或卡池发布时，验收应覆盖保存结果、版本引用和校验失败路径。
- 规则调整应单独记录裁决依据、受影响的行为和回归用例。
- 涉及架构边界的设计和实现审查必须核对模块归属、状态所有权与三类交互契约。
  用层级总图及各受影响层的模块图核对跨层交互，并用关键场景验证实际调用遵循契约。

## 治理

本章程适用于本项目的规格、计划、任务和变更审查。章程修订须记录原因、受影响模块、
兼容影响及迁移方式，经项目负责人确认后更新版本。原则删除或不兼容重定义提升主版本，
新增原则或实质扩展提升次版本，措辞澄清提升修订版本。变更审查须核对适用原则，
并在合入前处理发现的偏离。
